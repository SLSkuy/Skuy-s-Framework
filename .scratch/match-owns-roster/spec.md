# 合并房间进名册对象，玩法粘合点分开

Respect: `CONTEXT.md`, `docs/adr/0001-host-starts-match-late-join.md`, `docs/adr/0002-match-owns-roster-procedure-only-gates.md`.

## Problem Statement

玩家要的是：房主从菜单创建之后，别人直接加入已经在打的对局。现在却把同一寿命拆成会话壳加房间名册，流程里再切关再「开战」。要合并的是这两套名册/连接主人，不是把连接和玩法都塞进玩法粘合点。加入尚未被接受时也没有对局，却把连入挂在会话壳上。

## Solution

玩家只看见菜单和对局。本机玩或开多人立刻进入对局：名册、开听（若接远端）、入座一次完成。加入方在被接受前留在菜单，只有一条未入座的连接；接受后才有对局并加载关卡。名册与连接由合并后的对局名册对象负责；玩法由粘合点编排；关卡控制只负责加载和切换关卡。三者互不替代。回菜单只发生在房主退出或结束本机玩；加入方退出只除名。

## User Stories

1. As a 玩家, I want 从菜单选择本机玩、开多人、或加入, so that 我不必先理解房间或大厅。
2. As a 玩家, I want 未在对局时才出现那三个入口, so that 我不会在对局中再开一套对局。
3. As a 玩家, I want 可观察的流程只有菜单和对局, so that 加入等待不会变成第三站。
4. As a 本机玩玩家, I want 点本机玩后立刻进入对局, so that 单人与多人是同一条路径。
5. As a 本机玩玩家, I want 对局不接受远端加入且名册最多一人, so that 不会有人连进本机玩。
6. As a 本机玩玩家, I want 点本机玩时不开听远端, so that 本机玩不是半套联机。
7. As a 房主, I want 点开多人后本机立刻入座并进入对局, so that 我不在等人界面空等。
8. As a 房主, I want 一点开多人，对局就已经开始（不必等关卡加载或角色生成）, so that 加入方在切关途中也按中途入座处理。
9. As a 房主, I want 开听发生在进入对局时、在模拟钟转动之前, so that 别人能连上已经开始的对局。
10. As a 房主, I want 进入对局后由关卡控制加载关卡, so that 菜单流程不再负责切关。
11. As a 房主, I want 不要在切关后再经历一次「开战」, so that 离开菜单就是对局的全部含义。
12. As a 加入方, I want 点加入后先连接、被接受前仍在菜单且没有对局, so that 失败时不会留下假对局。
13. As a 加入方, I want 用现有客户端配置的地址和端口加入, so that 本阶段能在本机两进程验证，而不做房间码和发现。
14. As a 加入方, I want 加入过程不另开一套加入对象、也不重连, so that 被接受后仍是同一条连接。
15. As a 加入方, I want 被接受后才出现名册对象并写入名册（含我自己）, so that 名册不是空壳。
16. As a 加入方, I want 被接受后进入对局并由关卡控制加载关卡, so that 我和房主一样处在对局里，而不是菜单里切关。
17. As a 加入方, I want Join 响应告诉我是否被接受、我的玩家身份、房主身份、完整名册, so that 我能对齐房主的名册。
18. As a 加入方, I want 被拒绝、连接失败、名册已满或对局已解散时仍停在菜单并拆掉客户端网络, so that 我不会挂着一条废连接。
19. As a 加入方, I want 在未被接受时取消加入并回到干净菜单, so that 我不必等超时。
20. As a 加入方, I want 对局进行中仍能入座, so that 「主机先打、别人再进」成立。
21. As a 已在对局中的玩家, I want 看见当前名册（人数与玩家身份）, so that 我知道谁在这局里。
22. As a 已在对局中的加入方, I want 别人后来入座或离开时名册更新, so that 我看到的名单和房主一致。
23. As a 房主, I want 每次入座或离座后向在席加入方广播完整名册, so that 先到的人也能看见后到的人。
24. As a 后到的加入方, I want 进对局时拿到当时完整名册, so that 我不缺已经在局里的人。
25. As a 房主, I want 对局最多 4 名玩家, so that 满员时 Join 被拒绝。
26. As a 房主, I want 加入请求不把对方自报的传输身份当成玩家身份, so that 名册键始终是我分配的玩家身份。
27. As a 加入方, I want 连接身份只用于传输, so that 掉线按连接找到玩家并从名册删除。
28. As a 加入方, I want 离开对局后只从名册消失、对局对其他人继续, so that 我退出不会拆掉房主的局。
29. As a 房主, I want 离开对局时所有加入方回到菜单, so that 没有无主对局。
30. As a 本机玩玩家, I want 离开后回到菜单且对局消失, so that 本机路径和多人解散一致。
31. As a 加入方, I want 收到解散后回到菜单并拆掉客户端网络, so that 我不会对着已死的房主挂着。
32. As a 玩家, I want 关卡只承载几何与对局视野, so that 切关不会再启动第二套进程壳。
33. As a 玩家, I want 回菜单时重新看到菜单入口且只有一份进程壳, so that 不会叠两个核心对象。
34. As a 玩家, I want 对局期间用常驻调试 HUD 看名册并离开, so that 菜单画布卸掉之后我仍能操作。
35. As a 玩家, I want 对局中才允许 Tick 和模拟核, so that 菜单阶段不会跑战斗步进。
36. As a 开发者, I want UI 只对流程核心发意图, so that 界面不直接抓名册对象或玩法粘合点。
37. As a 开发者, I want 流程核心不加载关卡, so that 进出对局和关卡控制不会抢切场景。
38. As a 开发者, I want 名册、Admit、开听和连接映射在同一个名册对象上, so that 不再有会话壳加房间两套主人。
39. As a 开发者, I want 玩法粘合点不持有名册、不 Admit、不开听, so that 玩家连接和游戏玩法分得开。
40. As a 开发者, I want 关卡控制既不在名册对象里、也不由粘合点自己实现关卡规则, so that 粘合点只编排玩法。
41. As a 开发者, I want 第一期关卡控制可以很薄（只加载/切换关卡）, so that 启动链先通，关卡规则以后再长。
42. As a 开发者, I want 删除房间对象，名册对象仍在, so that 合并不等于拆掉连接这一侧。
43. As a 开发者, I want 菜单加入期间由流程核心登记客户端网络、接受后名册对象接管同一条连接, so that 没有第三套加入类型、也不重连。
44. As a 开发者, I want 本机玩与开多人直接创建名册对象、不经过客户端连接路径, so that 房主不会先当加入方。
45. As a 开发者, I want 进入对局时另有玩法粘合点, so that 后续玩法有胶水可挂，而不挂到连接层。
46. As a 开发者, I want 传输沙盒可以留下但不得成为对局主人, so that 仍能单独测传输。
47. As a 开发者, I want 未再使用的加入中流程态不要留在可编译路径里, so that 以后不会被误挂上。
48. As a 玩家, I want 本阶段不依赖角色互看或输入同步, so that 先验证进出对局和名册。
49. As a 房主, I want 在加入方 Join 尚未完成时仍视为对局已开始, so that 不会对同一加入方先说不在局里再说在局里。
50. As a 加入方, I want 不必等待房主模拟钟或 spawn 完成就能进关卡, so that 切关窗口不是第二道门闩。

## Implementation Decisions

- 流程核心仍是 UI 的唯一意图入口：本机玩、开多人、加入、离开。玩家可观察的流程态只有菜单与对局。加入尚未被接受不是流程态；用进行中的加入意图表示忙与可取消。
- 合并：房间对象并进名册对象。名册对象负责玩家身份分配、连接与玩家的映射、Admit、离座、解散、开听或接管已有客户端连接。网络 Handler 只适配消息。玩法粘合点不接收这些职责。
- 玩法粘合点只编排后续玩法（含启动模拟核、创建并调用关卡控制）。不持有名册、不映射连接、不开听。进入对局时与名册对象分开登记；拆除对局时一并注销。
- 本机玩：立刻登记名册对象（容量 1，不接远端，本机入座，不开听）和玩法粘合点，切到对局。开多人：立刻登记名册对象（容量 4，接远端，本机入座并开听）和玩法粘合点，切到对局。
- 加入：流程核心登记客户端网络并收「加入已决」。成功则登记名册对象、接管同一条连接（不重连）、登记玩法粘合点、切到对局。失败或取消则注销客户端网络，保持菜单，不得留下名册对象或粘合点。不引入短命加入类型。
- 关卡控制第一期即独立：只负责加载与切换关卡。进入对局流程态后由玩法粘合点调用它去加载关卡。离开对局回到菜单时，由流程核心加载菜单入口场景。流程的对局态不再监听「关卡就绪后再开战」。
- 没有第二次开战 API。模拟核由玩法粘合点启动；可以晚于开听，但不是玩家可感知的第二道门闩。
- 房主分配单调递增的玩家身份；本机连接用固定的本地连接键映射到该身份。加入响应带回：是否接受、自己的玩家身份、房主玩家身份、完整名册。接受即进入已经开始的对局。
- 入座或离座后，房主对仍在席的加入方广播完整名册。加入方离座只除名并广播；房主离座或名册对象拆除即解散：停玩法、清名册、停网络、通知加入方、流程回菜单。
- 对局调试 HUD 仍挂常驻 UI：显示名册；加入方离开；房主解散。UI 不得直接抓名册对象或粘合点。
- 语言以领域词表为准。避免把玩法粘合点叫成名册，也避免再引入房间。

## Testing Decisions

- 只测对外行为：意图之后是否有对局、名册是否对齐、流程态是否为菜单或对局、是否开听、关卡控制是否被要求加载关卡、失败/取消后是否无对局且无客户端网络。不测私有字段、核内部步进。不把「粘合点上能否读到名册」当成正确断言——名册不在粘合点上。
- **接缝（仅此一条）：名册对象对外的对局连接/名册 API，以及它发出/收下的加入与名册消息。** 流程核心编排何时创建名册对象与玩法粘合点、菜单加入时登记/注销客户端网络。能在不连真实传输的情况下向名册对象注入「某连接加入请求 / 加入响应 / 连接移除」，并读取名册、是否接远端、本进程是房主还是加入方。玩法粘合点不是这条接缝；不要用它来 Admit。
- 仓库里几乎没有对等的 EditMode 玩法测试；上一刀以战局管理器为接缝，本刀仍是同一高度：合并后的名册对象，而不是换成粘合点。
- 好测试的例子：本机玩之后容量 1 且再 Admit 远端失败、且未开听；开多人后加入响应含完整名册；满员拒绝且被拒方无对局；加入方离开名册减少但对局仍在；房主离开后双方无对局；加入失败或取消后无名册对象、流程仍为菜单、客户端网络已拆；进入对局后关卡控制被调用一次，流程核心没有第二次开战入口。

## Out of Scope

准备就绪、房间码、局域网发现、IP 输入 UI、重连、房主迁移、再来一局、中途加入后的角色互看、玩家输入与世界快照、预测/插值、非玩家实体、dedicated、把传输测试改成对局主人、关卡规则/刷怪/胜负、pawn spawn。

## Further Notes

上一刀把「房间」做成名册权威，与对局寿命重合，所以要合并进名册对象。玩法粘合点从一开始就不是名册权威，不能当成合并的落点。`Join_Response` 历史上曾规划 `inMatch` 字段，本刀以「接受即已在对局」取代，不恢复该字段。
